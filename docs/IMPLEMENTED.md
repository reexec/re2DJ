# 구현 완료 항목 / Implemented

완료된 구현·검증 항목을 누적 기록합니다. 상세 근거는 각 작업 로그와 설계 문서를 참조합니다.

*This document records completed implementation and verification items. Detailed evidence remains in the corresponding design and work-log documents.*

- **#27 — 화면 셰이더가 여러 pass를 잇고(`.glslp`), 내장 `fsr`에 RCAS를, `scalefx`·`anime4k`를 더했습니다.** libretro preset의 부분집합(pass별 셰이더·배율·필터·float 대상, `OrigTexture`, `PassPrevN`)을 읽어 pass마다 FBO에 그리고 마지막만 창에 그립니다. 내장은 포함 파일 묶음이 되었습니다. `fsr`는 EASU 뒤 RCAS 선명화, `scalefx`는 ScaleFX 다섯 pass 원본(픽셀아트용, EZ2DJ의 CG에는 윤곽이 딱딱해짐), `anime4k`는 Anime4K CNN x2 (S)를 mpv 훅에서 변환한 것입니다. 4th 4K 전체 화면 vsync off: `none` 799, `fsr` 688, `scalefx` 538, `anime4k` 565fps. 근거: [설계](design/20261025-i027-multipass-screen-shaders.md), [작업 로그](work-logs/20261025-i027-multipass-screen-shaders.md).

  *#27 — screen shaders chain passes (`.glslp`), the built-in `fsr` gains RCAS, and `scalefx` and `anime4k` are added: a subset of the libretro preset format (per-pass shaders, scales, filters and float targets, `OrigTexture`, `PassPrevN`) is read, each pass drawn into a framebuffer and only the last into the window, and built-ins became embedded file sets. `fsr` is EASU then RCAS sharpening, `scalefx` ScaleFX's five passes unchanged (for pixel art; EZ2DJ's CG gets hard outlines), `anime4k` Anime4K CNN x2 (S) converted from its mpv hooks. 4th fullscreen at 4K with vsync off: `none` 799, `fsr` 688, `scalefx` 538, `anime4k` 565 fps. Evidence: [design](design/20261025-i027-multipass-screen-shaders.md), [work log](work-logs/20261025-i027-multipass-screen-shaders.md).*

- **#26 — 내장 화면 셰이더 `fsr`(AMD FSR 1 EASU)를 더했습니다.** DLSS 같은 시간 누적 업스케일러는 모션 벡터·깊이가 없는 2D 게임에 맞지 않아, 프레임 하나만 보는 FSR 1의 업스케일 단계를 단일 pass로 옮겼습니다. 4K 전체 화면(4.5배)에서 `none`보다 글자·로고 경계가 선명하고, 4th vsync off 처리량은 4~9% 줄었습니다(RTX 4090). `--post-shader fsr`나 OSD로 고릅니다. 근거: [설계](design/20261025-i026-fsr-screen-shader.md), [작업 로그](work-logs/20261025-i026-fsr-screen-shader.md).

  *#26 — a built-in screen shader `fsr` (AMD FSR 1 EASU): temporal upscalers like DLSS do not fit a 2D game without motion vectors or depth, so FSR 1's upscaling pass, which looks at one frame, was ported as a single pass; fullscreen at 4K (4.5x) text and logo edges are sharper than under `none`, at 4 to 9% of 4th's vsync-off throughput (RTX 4090). Chosen with `--post-shader fsr` or in the OSD. Evidence: [design](design/20261025-i026-fsr-screen-shader.md), [work log](work-logs/20261025-i026-fsr-screen-shader.md).*

- **#25 — in-process 러너의 import 경로와 DirectDraw `Clear` 비용을 줄였고, `--vsync` 옵션을 더했습니다.** vsync off 실행을 바깥에서 샘플링 프로파일하니, import마다 export를 이름으로 다시 찾는 비용(모듈 이름 정규화 포함)과 `Clear`가 프레임마다 화면 버퍼를 세 번 훑는 비용이 컸습니다. 게이트 주소별 캐시·색인과 한 번 채우기로 vsync off 처리량이 게임에 따라 6~43%, `Clear`를 쓰는 게임은 그 위에 17~26% 올랐습니다. `--vsync on|off|adaptive`로 측정용 vsync off를 고릅니다. 근거: [설계](design/20261012-i025-import-path-and-clear-costs.md), [작업 로그](work-logs/20261012-i025-import-path-and-clear-costs.md).

  *#25 — the in-process runner's import path and DirectDraw `Clear` cost less, and `--vsync` is an option: an outside sampling profile of vsync-off runs showed each import looking its export up by name again (module-name normalization included) and `Clear` passing over the screen buffer three times a frame; a per-gate-address cache and index and a one-pass fill raised vsync-off throughput by 6 to 43% per game, and by 17 to 26% more for the games using `Clear`. `--vsync on|off|adaptive` picks vsync off for measuring. Evidence: [design](design/20261012-i025-import-path-and-clear-costs.md), [work log](work-logs/20261012-i025-import-path-and-clear-costs.md).*

- **#24 — 읽었던 CHD 경로를 기억해 다음 실행에서 미리 읽습니다.** 게스트가 CHD에서 읽은 경로(조회·목록·읽기)를 overlay의 `.re2dj-readahead`에 사용 횟수와 함께 남기고, 다음 실행은 두 번 이상 쓰인 경로를 게스트가 한가할 때 미리 읽어 OS 캐시에 올립니다. 곡 로딩의 대부분(패널·이펙트·랭킹·디렉터리 항목)은 곡과 관계없이 같기 때문입니다. HDD에서 캐시를 비운 6th 데모의 곡 로딩은 기록 없이 2.17·1.33초, 두 실행 분 기록으로 0.58·0.65초였습니다. 폴더 통째 미리 읽기는 CHD 안에서 폴더가 흩어져 있어 효과가 없었고 넣지 않았습니다. 근거: [설계](design/20261012-i024-learned-chd-read-ahead.md), [작업 로그](work-logs/20261012-i024-learned-chd-read-ahead.md).

  *#24 — the CHD paths read are remembered and read ahead in later runs: the paths the guest reads from the CHD (lookups, listings, reads) go into the overlay's `.re2dj-readahead` with use counts, and the next run reads those used more than once into the OS cache while the guest is idle, since most of a song load (panels, effects, rankings, directory entries) is the same for every song. 6th's demo song loads from an HDD with the caches emptied took 2.17 and 1.33 s with no journal and 0.58 and 0.65 s with two runs' journal. Reading whole directories ahead did not help, the directories lying scattered in the CHD, and was left out. Evidence: [design](design/20261012-i024-learned-chd-read-ahead.md), [work log](work-logs/20261012-i024-learned-chd-read-ahead.md).*

- **#22 — 패드의 LT+RT+Y로 OSD를 열고 패드로 조작합니다(rePIU #55).** 한 패드에서 세 입력을 누르는 순간 OSD가 열리고 닫힙니다. 열려 있는 동안 패드는 OSD 탐색(D-pad·왼쪽 스틱 이동, A 선택, B로 메뉴 닫기나 메뉴가 없으면 OSD 닫기)에만 쓰이고 게임에는 가지 않으며, 닫을 때 누르고 있던 입력은 뗄 때까지 게임에 숨깁니다. 키보드는 그대로 게임에 갑니다. 근거: [설계](design/20261011-i022-pad-osd.md), [작업 로그](work-logs/20261011-i022-pad-osd.md).

  *#22 — LT+RT+Y on a pad opens the OSD and the pad drives it (rePIU #55): the three pressed on one pad toggle it at once; while it is open the pad only navigates it (the d-pad or left stick moves, A chooses, B closes a menu or, with none open, the OSD) and none of it reaches the game, input held as it closes staying hidden from the game until released; the keyboard still reaches the game. Evidence: [design](design/20261011-i022-pad-osd.md), [work log](work-logs/20261011-i022-pad-osd.md).*

Evidence: [design](design/20261010-i020-pad-quit-combination.md), [work log](work-logs/20261010-i020-pad-quit-combination.md).*

- **#17 — 런처가 새 릴리스를 알리고 Update 버튼으로 설치합니다(rePIU #48). 산출물 이름은 `re2DJ-v*`입니다.** 런처가 열리면 GitHub 최신 릴리스를 백그라운드에서 확인하고, 더 새 버전이 있으면 알림과 Update 버튼을 보여 줍니다. 이 빌드용 아카이브를 받아 GitHub `digest`(SHA-256)로 검증하고 풀어 아카이브의 파일만 제자리에서 바꾼 뒤, Linux는 `execv`로 같은 프로세스에서, Windows는 자식으로 다시 시작합니다. 실행 파일 옆 `VERSION`이 맞는 릴리스 설치에서만 교체하고, 실패하면 모두 되돌립니다. 산출물은 `re2DJ-v<ver>-<platform>`이고 안의 실행 파일은 `re2dj` 그대로입니다. 근거: [설계](design/20261010-i017-launcher-self-update.md), [작업 로그](work-logs/20261010-i017-launcher-self-update.md), [가이드](guides/launcher-update.md).

  *#17 — the launcher announces a new release and installs it with an Update button (rePIU #48), and artifacts are named `re2DJ-v*`: when the launcher opens it checks GitHub's latest release in the background and, for a newer one, shows a notice and Update; that downloads this build's archive, checks it against GitHub's `digest` (SHA-256), unpacks it, replaces only the archive's files in place, and restarts in the same process through `execv` on Linux or as a child on Windows. Only a release install whose `VERSION` next to the executable matches is replaced, and any failure is rolled back. Artifacts are `re2DJ-v<ver>-<platform>`, the executable inside still `re2dj`. Evidence: [design](design/20261010-i017-launcher-self-update.md), [work log](work-logs/20261010-i017-launcher-self-update.md), [guide](guides/launcher-update.md).*

- **#15 — ez2dj3rd가 in-process 러너에서 실행됩니다.** 3rd 덤프는 창 모드 DirectDraw(`DDSCL_NORMAL`)를 써서 `user32!GetClientRect`에서 멈췄습니다. user32 `GetClientRect`·`ClientToScreen`과 `IDirectDrawClipper`(`CreateClipper`, `SetHWnd`, 서피스 `SetClipper`·`GetClipper`)를 모델링해, 오프스크린을 primary로 `Blt`하는 프레임이 표시되고 곡 플레이까지 진행합니다. 근거: [설계](design/20261010-i015-ez2dj3rd-windowed-ddraw.md), [작업 로그](work-logs/20261010-i015-ez2dj3rd-windowed-ddraw.md).

  *#15 — ez2dj3rd runs on the in-process runner: its dump uses windowed DirectDraw (`DDSCL_NORMAL`) and stopped at `user32!GetClientRect`. With user32 `GetClientRect` and `ClientToScreen` and `IDirectDrawClipper` (`CreateClipper`, `SetHWnd`, surface `SetClipper` and `GetClipper`) modelled, the frames it blits from offscreen onto the primary show and play reaches a song. Evidence: [design](design/20261010-i015-ez2dj3rd-windowed-ddraw.md), [work log](work-logs/20261010-i015-ez2dj3rd-windowed-ddraw.md).*

- **#14 — 전체 화면과 비율 유지를 OSD와 런처에서 바꾸고 `cfg/re2dj.ini`에 저장합니다(rePIU #45·#34).** 비율 유지를 끄면 그림이 창 전체를 채웁니다(`--stretch`, 기본은 켬). 게임 창의 OSD 맨 위에 두 체크박스가 생겼고, Alt+Enter로도 전체 화면을 바꿉니다(Enter는 게임에 넘기지 않음). OSD·Alt+Enter·더블클릭으로 바꾼 값은 저장되고, 모든 실행이 명령줄 → 설정 파일 → 기본값 순으로 시작 값을 정합니다. 런처는 Options 맨 위의 두 체크박스를 따라 창도 전체 화면·비율 유지 배치로 그리며, 표에서 Space는 선택만 합니다. EZ2DJ 게임패드 기본값은 1P 키 십자키 왼쪽·위·`A`·`Y`·`B`, 페달 `X`, 이펙터 `LB`·`RB`·`LT`·`RT`로 바꿨습니다. 근거: [설계](design/20261010-i014-fullscreen-keep-aspect.md), [작업 로그](work-logs/20261010-i014-fullscreen-keep-aspect.md).

  *#14 — fullscreen and keep-aspect change in the OSD and the launcher and are kept in `cfg/re2dj.ini` (rePIU #45, #34): with keep-aspect off the picture fills the window (`--stretch`; on by default). The game window's OSD has both checkboxes at the top, and Alt+Enter switches fullscreen too (its Enter withheld from the game). Values changed through the OSD, Alt+Enter or a double click are saved, and every run takes its start-up values from the command line, then the file, then the defaults. The launcher follows its two top Options checkboxes for its own window too, and Space only selects on its table. EZ2DJ's gamepad defaults became the d-pad's left and up, `A`, `Y` and `B` for player 1's keys, `X` for the pedal and `LB`, `RB`, `LT` and `RT` for the effectors. Evidence: [design](design/20261010-i014-fullscreen-keep-aspect.md), [work log](work-logs/20261010-i014-fullscreen-keep-aspect.md).*

- **#9 — 게임이 나눠 읽는 CHD 파일을 백그라운드에서 미리 읽습니다.** 6th는 메인 스레드가 133ms마다 배경음 `.ezw`를 `ReadFile`로 스트리밍하므로, HDD에 둔 CHD를 처음 읽는 조각마다 25~480ms씩 멈췄습니다. 이제 첫 `Read` 뒤 256KiB 이상 남은 이미지 파일은 작업 스레드가 메모리에 미리 읽고, 이후 읽기는 메모리에서 돌려줍니다. 게스트가 CHD를 쓰는 동안에는 작업 스레드가 비켜섭니다. SpaceMix 플레이와 35분 어트랙트에서 곡 재생 중 느린 읽기가 없어졌습니다. 근거: [설계](design/20261009-i009-chd-file-prefetch.md), [작업 로그](work-logs/20261009-i009-chd-file-prefetch.md).

  *#9 — CHD files the game reads in pieces are read ahead in the background: 6th's main thread streams its music `.ezw` with `ReadFile` every 133 ms, so each CHD piece read for the first time from an HDD stalled it for 25 to 480 ms. An image file with at least 256 KiB left after its first `Read` is now read into memory by a worker thread and later reads come from memory, the worker stepping aside while the guest uses the CHD. A SpaceMix play and a 35-minute attract showed no slow read during a song. Evidence: [design](design/20261009-i009-chd-file-prefetch.md), [work log](work-logs/20261009-i009-chd-file-prefetch.md).*

- **#4 — 같은 PC에서 Windows와 Linux x86·x64 성능을 비교했습니다.** vsync on에서는 모두 60 fps이고 Linux x64의 CPU가 가장 낮습니다. vsync off 처리량은 Linux x64가 Windows in-process의 ×0.98~×3.37, x86이 ×0.54~×1.03입니다. x86의 격차는 주로 NVIDIA 32비트 `egl-wayland` v1 경로에서 옵니다. 근거: [분석](analysis/linux-windows-performance.md), [작업 로그](work-logs/20261005-i004-linux-windows-performance.md).

  *#4 — compared Windows with Linux x86 and x64 on one PC: all hold 60 fps with vsync on and Linux x64 uses the least CPU; vsync-off throughput on Linux x64 is ×0.98 to ×3.37 of the Windows in-process runner and on x86 ×0.54 to ×1.03, x86's gap coming mainly from NVIDIA's 32-bit `egl-wayland` v1 path. - **작업 291 — 3rd 프레임률이 SDL3의 타이머 해상도 요청에 얹혀 있음을 확정했습니다.** 3rd는 `timeBeginPeriod`를 한 번도 부르지 않는데(원본 파일 전체 검색 0건) NT 계열 기본 해상도 15.625 ms에서는 살아남을 수 없는 sleep 기반 리미터를 씁니다. 해상도를 올리는 것은 정적 링크된 **SDL3**이며, 서브시스템 하나만 초기화해도 `SDL_InitTicks`가 기본 힌트로 `timeBeginPeriod(1)`을 부릅니다. `SDL_TIMER_RESOLUTION=0`으로 그 요청만 제거하자 `Sleep` p50이 16.0 ms에서 27.5 ms로, 프레임률이 56.9 fps에서 **32.7 fps로 절반이 되었습니다.** 또한 게스트의 주기 계산이 고정 상수가 아니라 `목표 - 경과` 피드백임을 확정했습니다. 요청값과 직전 작업 시간의 상관이 -0.78~-0.98인데 둘의 **합은 16.94~17.35 ms로 일정**하며, 호스트 해상도를 바꿔도 움직이지 않습니다. 목표 주기는 60 Hz의 16.67 ms가 아니라 약 17 ms(58.8 Hz)로 추정되며 원본 상수 확인은 미확정입니다. `NtQueryTimerResolution`은 시스템 전역 값을 읽으므로 이 의존을 볼 수 없다는 점도 확인했습니다. 후속 측정에서 `timeGetTime`은 함께 뭉개지지 않음을 확인했으므로(같은 프로세스에서 시계 1 ms, `Sleep(15)` p50 25.87 ms), 요청을 잃었을 때 손상되는 것은 프레임률이고 게스트의 내부 시간 진행은 유지됩니다. 진단은 모두 `--guest-wait-trace`로만 켜집니다. 근거: [설계](design/20260915-291-timer-resolution-dependency.md), [작업 지시](work-orders/20260915-291-timer-resolution-dependency.md), [작업 로그](work-logs/20260915-291-timer-resolution-dependency.md), [분석](analysis/ez2dj3rd-frame-pacing.md), [배경](kb/windows-timer-resolution.md).

  *Task 291 — established that 3rd's frame rate rides on SDL3's timer-resolution request. 3rd never calls `timeBeginPeriod` (zero hits across the whole original file) yet uses a sleep-based limiter that cannot survive the NT family's 15.625 ms default. What raises the resolution is statically linked **SDL3**: initializing any subsystem takes `SDL_InitTicks` through its default hint into `timeBeginPeriod(1)`. Removing only that request with `SDL_TIMER_RESOLUTION=0` moved the `Sleep` p50 from 16.0 ms to 27.5 ms and **halved the frame rate from 56.9 fps to 32.7 fps.** The guest's period was also established as `target - elapsed` feedback rather than a fixed constant: the request correlates -0.78 to -0.98 with the preceding work while **their sum holds at 16.94-17.35 ms**, unmoved by changing the host resolution. That target is estimated at about 17 ms (58.8 Hz) rather than 60 Hz's 16.67 ms, with the original constant left unresolved. `NtQueryTimerResolution` was also shown unable to see this dependency, since it reads the system-wide value. A follow-up measurement confirmed `timeGetTime` does not degrade with it — a 1 ms clock beside a 25.87 ms `Sleep(15)` p50 in one process — so losing the request costs frame rate while the guest's internal advance of time holds. Every diagnostic is enabled only by `--guest-wait-trace`. Evidence: [design](design/20260915-291-timer-resolution-dependency.md), [work order](work-orders/20260915-291-timer-resolution-dependency.md), [work log](work-logs/20260915-291-timer-resolution-dependency.md), [analysis](analysis/ez2dj3rd-frame-pacing.md), and [background](kb/windows-timer-resolution.md).*
